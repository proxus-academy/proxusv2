# Effect CLI and child processes

> **Version:** Effect v4 beta. The repository currently pins `effect@4.0.0-beta.98`; the source snapshot used for this guide is `4.0.0-beta.98` (`3e4abbcb0d0e9a5e82b6b88c7ef7ab69900105ec`). Re-check signatures before upgrading.
>
> **API status:** every API imported from `effect/unstable/cli` or `effect/unstable/process` is **unstable**. It may change during the v4 beta without a stable-major-version break. Keep these imports behind application-owned modules.

This guide treats a CLI command as a transport adapter and process execution as an infrastructure adapter. Command handlers decode terminal input, call an application module, render output, and select an exit status. They should not own product behavior.

## A complete typed CLI

Arguments are positional; flags are named. In the current parser, flags must precede positional arguments (`cmd --flag value`, not `cmd value --flag`). `--help` and `--version` are generated by `Command.run`.

```ts
import { NodeRuntime, NodeServices } from "@effect/platform-node"
import { Console, Effect, Layer, Schema } from "effect"
import { Argument, Command, Flag } from "effect/unstable/cli" // UNSTABLE

const TaskId = Schema.String.pipe(Schema.brand("TaskId"))
type TaskId = typeof TaskId.Type

const workspace = Flag.string("workspace").pipe(
  Flag.withAlias("w"),
  Flag.withDescription("Workspace to operate on"),
  Flag.withDefault("personal")
)

const root = Command.make("tasks").pipe(
  Command.withDescription("Manage tasks"),
  Command.withSharedFlags({
    workspace,
    verbose: Flag.boolean("verbose").pipe(Flag.withAlias("v"))
  })
)

const show = Command.make(
  "show",
  {
    id: Argument.string("id").pipe(
      Argument.withSchema(TaskId),
      Argument.withDescription("Task identifier")
    ),
    format: Flag.choice("format", ["text", "json"]).pipe(
      Flag.withDefault("text")
    )
  },
  Effect.fn("cli.tasks.show")(function*({ id, format }) {
    const parent = yield* root
    if (parent.verbose) {
      yield* Console.error(`workspace=${parent.workspace} action=show`)
    }

    // Replace with a call to the application service.
    const task = { id, title: "Ship Effect v4" }
    yield* Console.log(
      format === "json" ? JSON.stringify(task) : `${task.id}: ${task.title}`
    )
  })
).pipe(
  Command.withDescription("Show one task"),
  Command.withAlias("get"),
  Command.withExamples([{
    command: "tasks --workspace team-a show task-1 --format json",
    description: "Print one task as JSON"
  }])
)

const app = root.pipe(Command.withSubcommands([show]))

app.pipe(
  Command.run({ version: "1.0.0" }),
  Effect.provide(NodeServices.layer),
  NodeRuntime.runMain
)
```

### Argument and flag reference

```ts
Argument.string("file")                        // required positional text
Argument.integer("count")                     // required positional integer
Argument.string("output").pipe(Argument.optional)
Argument.string("format").pipe(Argument.withDefault("json"))
Argument.string("files").pipe(Argument.variadic()) // zero or more
Argument.string("files").pipe(Argument.atLeast(1)) // one or more

Flag.boolean("verbose").pipe(Flag.withAlias("v"))
Flag.string("output").pipe(Flag.withAlias("o"))
Flag.string("config").pipe(Flag.optional)
Flag.choice("format", ["json", "yaml", "toml"])
Flag.integer("count").pipe(Flag.withDefault(10))
```

Use descriptions and examples as part of the interface: they drive generated help and are user-facing compatibility commitments. Shared flags are explicit; a subcommand reads them by yielding its parent command.

## Child-process patterns

Never build a shell command by concatenating untrusted strings. `ChildProcess.make(program, argv)` keeps the executable and arguments separate and avoids shell interpretation unless the selected executable is itself a shell.

```ts
import { NodeServices } from "@effect/platform-node"
import { Console, Context, Effect, Layer, Schema, Stream, String } from "effect"
import { ChildProcess, ChildProcessSpawner } from "effect/unstable/process" // UNSTABLE

class ToolError extends Schema.TaggedErrorClass<ToolError>()("ToolError", {
  operation: Schema.String,
  cause: Schema.Defect
}) {}

class ToolRunner extends Context.Service<ToolRunner, {
  readonly version: Effect.Effect<string, ToolError>
  changedFiles(baseRef: string): Effect.Effect<ReadonlyArray<string>, ToolError>
  readonly lint: Effect.Effect<void, ToolError>
}>()("app/ToolRunner") {
  static readonly layer = Layer.effect(
    ToolRunner,
    Effect.gen(function*() {
      const spawner = yield* ChildProcessSpawner.ChildProcessSpawner
      const mapError = (operation: string) => (cause: unknown) =>
        new ToolError({ operation, cause })

      const version = spawner.string(
        ChildProcess.make("node", ["--version"])
      ).pipe(
        Effect.map(String.trim),
        Effect.mapError(mapError("node.version"))
      )

      const changedFiles = Effect.fn("ToolRunner.changedFiles")(function*(baseRef: string) {
        yield* Effect.annotateCurrentSpan({ baseRef })
        return yield* spawner.lines(
          ChildProcess.make("git", ["diff", "--name-only", `${baseRef}...HEAD`])
        ).pipe(Effect.mapError(mapError("git.diff")))
      })

      const lint = Effect.gen(function*() {
        const handle = yield* spawner.spawn(
          ChildProcess.make("pnpm", ["lint"], {
            env: { FORCE_COLOR: "1" },
            extendEnv: true
          })
        ).pipe(Effect.mapError(mapError("lint.spawn")))

        yield* handle.all.pipe(
          Stream.decodeText(),
          Stream.splitLines,
          Stream.runForEach((line) => Console.log(`[lint] ${line}`)),
          Effect.mapError(mapError("lint.output"))
        )

        const code = yield* handle.exitCode.pipe(
          Effect.mapError(mapError("lint.wait"))
        )
        if (code !== ChildProcessSpawner.ExitCode(0)) {
          return yield* new ToolError({
            operation: "lint.exit",
            cause: new Error(`lint exited with ${code}`)
          })
        }
      }).pipe(Effect.scoped)

      return ToolRunner.of({ version, changedFiles, lint })
    })
  ).pipe(Layer.provide(NodeServices.layer))
}
```

Choose the smallest execution mode that fits:

- `spawner.string(command)`: collect all output as one string; only for bounded output.
- `spawner.lines(command)`: collect line-oriented output; only for bounded line counts.
- `spawner.spawn(command)`: obtain a scoped handle and stream while the process runs.
- `ChildProcess.pipeTo(right)`: compose process values into a pipeline, for example `git log | head`.
- `handle.all`: combined output stream; consume it before awaiting or alongside the exit code so a full OS pipe cannot deadlock the child.
- `handle.exitCode`: typed exit status; explicitly reject non-zero codes when they mean failure.

## Lifecycle, cancellation, and resources

`spawn` requires `Scope`. Wrap the whole acquire/use/wait sequence in `Effect.scoped`, or put it in a scoped layer. Scope closure interrupts and cleans up the child according to the platform adapter. Do not return a live handle from an effect whose scope has already closed.

For long-running commands:

1. stream output instead of collecting it;
2. apply an explicit timeout at the application operation;
3. allow interruption to propagate—do not detach a child fiber;
4. await the exit code;
5. make termination behavior platform-specific only inside the process adapter;
6. keep shutdown under `NodeRuntime.runMain`, not `process.on(...)` scattered through handlers.

A process pipeline is one lifecycle: failure, cancellation, and stream consumption must cover every member. Test cancellation and timeout behavior, not only successful completion.

## Errors and exit behavior

Separate these cases:

- **CLI parse/help/version output:** owned by `Command.run` and the CLI module.
- **Expected application failures:** tagged domain errors; render concise stderr and map to a documented non-zero exit code at one top-level seam.
- **Spawn/platform failures:** executable missing, invalid cwd, permissions, broken streams; map to a narrow adapter error with operation context.
- **Non-zero child exit:** inspect `exitCode`; spawning successfully does not imply command success.
- **Defects:** unexpected programmer/runtime failures; preserve the cause for logs while avoiding secret leakage in terminal output.
- **Interruption:** cancellation/shutdown, not a domain failure; do not catch and convert it indiscriminately.

Keep stdout machine-readable when `--json` is selected. Send diagnostics and progress to stderr. Never print stack traces, environment maps, tokens, or raw provider responses by default.

## Configuration

Configuration belongs beside the module that consumes it. Use `Config`, never ad-hoc `process.env` parsing:

```ts
import { Config, Effect, Layer } from "effect"

const ProcessPolicyLayer = Layer.unwrap(Effect.gen(function*() {
  const maxParallel = yield* Config.int("TOOLS_MAX_PARALLEL")
  const allowFixes = yield* Config.boolean("TOOLS_ALLOW_FIXES")
  return makeProcessPolicyLayer({ maxParallel, allowFixes })
}))
```

Required values have no default and fail initialization. Use `Config.option` only when absence is intentional and `Config.withDefault` only for a real product default. Prefer `Config.nonEmptyString`, `Config.int`, `Config.port`, and `Config.boolean`.

## Security

- Use executable plus argument arrays; avoid `sh -c`, `bash -c`, `eval`, and interpolated tagged templates for untrusted input.
- Validate identifiers, refs, paths, and choices before execution. A branded string is not sanitization by itself.
- Resolve paths against an allowed root; reject traversal and unexpected symlink targets where relevant.
- Prefer an executable allowlist. Do not let user input select arbitrary binaries.
- Set the minimum environment. `extendEnv: true` inherits secrets; use it only deliberately and never log the resulting environment.
- Run with least OS privilege; constrain cwd, filesystem access, network access, time, concurrency, and output size.
- Treat child stdout/stderr as untrusted data. Bound collection, decode explicitly, and sanitize before logs/UI.
- Do not accept shell fragments as “arguments.” If shell syntax is required, put a reviewed script under source control and invoke it with validated arguments.
- Pin tools used in CI and account for platform differences in quoting, signals, and executable names.

## Testing

Test the interface through layers rather than invoking real tools in every unit test.

1. Put process use behind an application-owned `ToolRunner` interface.
2. Unit-test command/use-case behavior with `Layer.succeed(ToolRunner, fake)` and deterministic exits/output.
3. Test argument decoding, aliases, defaults, shared flags, help, malformed input, and stdout/stderr contracts.
4. Add focused Node integration tests for the live adapter using harmless, portable commands such as the current Node executable.
5. Cover spawn failure, non-zero exit, malformed text, large/streamed output, timeout, cancellation, and scope cleanup.
6. Never depend on a developer's global PATH, Git configuration, credentials, network, or repository state.
7. Assert machine output as parsed JSON, not snapshots polluted by colors or diagnostics.

## Anti-patterns

- Calling `process.env`, `process.exit`, `child_process.exec`, or `console.log` throughout domain modules.
- Treating a successful spawn as a successful command without checking `exitCode`.
- Collecting unbounded output with `string` or `lines`.
- Spawning outside `Effect.scoped` or leaking the handle beyond its scope.
- Concatenating input into shell commands.
- Putting business rules, persistence, or authorization directly in a `Command.make` handler.
- Catching every failure as `unknown`, losing typed domain errors and interruption semantics.
- Mixing JSON output and human diagnostics on stdout.
- Hiding required configuration behind defaults.
- Exposing unstable CLI/process imports across many modules instead of one seam.

## Review checklist

- [ ] Exact Effect v4 beta versions are pinned together.
- [ ] `effect/unstable/cli` and `effect/unstable/process` usage is explicitly marked unstable and localized.
- [ ] Command help, examples, aliases, and output/exit contracts are documented.
- [ ] Handlers call application modules and remain transport adapters.
- [ ] Spawned handles live inside a scope; cancellation and shutdown are tested.
- [ ] Output strategy is bounded or streaming, and non-zero exits are handled.
- [ ] Arguments are arrays; executable/path/environment inputs are validated and constrained.
- [ ] Required config uses typed `Config` and fails early.
- [ ] Expected failures, operational failures, defects, and interruption remain distinct.
- [ ] Unit tests use fake layers; focused integration tests exercise the platform adapter.
